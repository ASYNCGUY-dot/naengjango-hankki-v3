# 추천 이름 계산 캐시 검증 (2026-10-22)

기준 커밋은 `95353f939e8f929a509095b34a942aa164871280`이다. 추천의 순위 규칙을 바꾸지 않고
단백질 판정·재료명 정리·수량 없는 태그 분류에 각각 최대 8,192개 LRU 캐시를 둔다.
태그 분류 안에서 부르는 `display_name`의 반복도 함께 줄므로 별도 네 번째 캐시는 만들지 않는다.
공유 모듈의 함수, 사용자별 결과, 후보/재료 DB 조회는 캐시하지 않는다.

## 재현

```powershell
.venv/Scripts/python.exe scripts/benchmark_recommendation.py --database data/app.db --baseline 95353f9 --runs 9 --out docs/evidence/2026-10-22_recommendation_cache/results.json
.venv/Scripts/python.exe -m pytest tests/test_recommendation_cache.py -q
```

벤치마크는 로컬 SQLite를 읽기 전용으로 열고 승인 레시피와 그 재료·태그만 읽는다.
`results.json`에 데이터셋 지문, 모든 측정값, 입력별 결과 지문을 남긴다.
DB 자체는 저장소에 올리지 않는다. 다른 DB로 실행하면 데이터셋 지문이 달라진다.

7가지 입력 조합마다 이전 커밋과 수정본의 전체 결과(순서와 모든 필드)를 비교하고,
캐시가 빈 첫 호출과 채워진 다음 호출 모두 같아야 진행한다. 시간은 생선·고기·채소 6개 입력으로
9회 측정하며 두 SQL 조회·점수 계산을 포함한다. 매 회 모든 캐시를 비운 cold와 그 직후 warm을 구분한다.
두 버전을 각각 순서대로 실행하므로 장시간 시스템 부하 변화까지 통제한 실험은 아니다.

로컬 데이터는 레시피 1,144개·재료 행 12,945개다. KAMIS 범위 측정에 쓴 운영 데이터의
12,963행과 다른 스냅샷이다. `results.json`이 이번 로컬 측정의 기준이며,
운영 HTTP 응답, Render CPU, 네트워크 왕복 시간은 포함하지 않는다.

회귀 검사는 캐시 전후 결과, 새 DB 재료 반영, 서로 다른 사용자 입력, 분류의 수량 의존성,
실제 점수 계산에서의 캐시 사용과 크기 제한을 확인한다. 운영 성능은 배포 뒤 별도로 재측정한다.
