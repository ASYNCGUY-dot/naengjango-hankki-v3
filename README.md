# 냉장고 한끼

냉장고에 있는 재료로 만들 수 있는 레시피를 추천하는 모바일 웹 앱이다.
알레르기가 있으면 그 재료가 든 메뉴를 추천에서 빼준다.

**https://naengjango-hankki-v3-web.onrender.com**

> 무료 서버라 첫 접속에 20~35초 걸린다(실측 22.9초, 33.0초 — 회차 편차가 크다).
> 화면에 "서버를 깨우는 중"이 뜨면 기다리면 된다. 두 번째부터는 즉시 뜬다.

---

## 무엇을 하는가

공공데이터의 조리식품 레시피 **1,146개**와 식품영양성분 **30만 건**을 재료 기준으로
연결한다. 가진 재료를 넣으면 겹치는 재료가 많은 순으로 정렬하고, 프로필의 알레르기·
건강목표·조리도구를 반영해 후보를 좁힌다.

| 화면 | 하는 일 |
|---|---|
| 홈 | 제철·간단하게·가볍게·든든하게 네 테마를 가로 줄로. 검색과 분류 필터 |
| 냉장고 | 재료 등록·유통기한 관리. 입력하면 실제 태그에서 자동완성 |
| 추천 | 냉장고 재료로 추천. **이 화면에서 재료를 바로 고쳐 다시 받을 수 있다** |
| 레시피 상세 | 재료·조리순서·영양성분·영상, 영양 적합도, 부족한 재료와 대체안, 추천하기·즐겨찾기, 후기 |
| 온보딩 | 알레르기·건강목표·조리도구·성별·연령대·병력 입력 |
| 마이 | 계정 정보, 즐겨찾기, 내가 올린 것으로 가는 길, 로그아웃 |
| 내 레시피 | 직접 만든 레시피 등록·수정·삭제, 공개 상태와 추천 수 확인 |
| 재료 정보 등록 | 공식 DB에 없는 재료의 영양 정보 제보 |
| 승인 대기 목록 | 관리자 전용. 이름이 겹치는 레시피와 재료 제보를 승인·거절 |
| 가입·로그인 | 약관 동의, 비밀번호 초기화 |

레시피 상세는 **로그인 없이 링크로 공유된다.** 후기도 로그인 없이 읽힌다.
추천하기·즐겨찾기·영양 적합도·후기 작성만 로그인 시 나타난다.

### 추천하기와 즐겨찾기는 다른 기능이다

**추천하기**(♥)는 남에게 보이는 공개 지표다. 이 수가 쌓이면 홈의 "많이 추천한 메뉴"에
오르고, 사용자가 등록한 레시피는 이 수가 기준을 넘어야 다른 사람의 추천 후보가 된다.
**즐겨찾기**(★)는 내가 다시 보려고 담아두는 것이고 나만 본다. 서버에서도 테이블이
갈라져 있다(`recipe_likes` vs `favorites`).

### 핵심은 알레르기 제외다

놓치는 자리가 둘이다. **태그를 다는 쪽**과 **태그로 거르는 쪽**이 각각 샌다.

거르는 쪽은 표기가 갈린다. `달걀`(200개)과 `계란`(27개)이 서로 다른 태그로 들어 있어
동의어를 묶는다. 운영 데이터로 확인했다 — 후보 832개 중 금지 태그가 새어나온 레시피
0개, `계란`만 붙은 27개도 전부 빠졌다.

다는 쪽은 더 크게 샜다. 알레르겐 이름이 재료에 **그대로** 있어야만 태그가 붙었는데,
"치즈"에는 "우유"라는 글자가 없고 "두부"에는 "대두"가 없다. 실제로 대두 알레르기를
고른 사람에게 두부가 든 레시피 153개가 하나도 안 걸러진 채 추천됐다. 파생 재료 사전을
넣고 기존 1,147개를 다시 태깅해 **153개 → 0개**가 됐다(`migration/008`).

반대 방향도 고쳤다. `게`를 문자열 포함으로 찾으면 **스파게티·바게트·얇게**가 전부
걸린다 — 게 태그 42개가 전부 이런 오탐이었다. 과잉 차단도 해롭다. 먹을 수 있는 것을
계속 빼면 사용자는 알레르기 입력을 지워버리고, 그러면 진짜 위험한 것도 안 걸러진다.

선택지는 화면이 지어내지 않고 **서버가 실제 태그에서 만들어 준다.** 목록에 없는 값을
고르게 하면 사용자는 골랐는데 필터는 아무것도 안 거르고, 본인은 걸러졌다고 믿는다.

같은 원칙을 성별·연령대·병력(`GET /profile/options`)과 냉장고 재료 자동완성
(`GET /pantry/suggest`)에도 적용했다. 화면이 서버의 판정 기준을 따로 들고 있으면 반드시
어긋나고, **어긋나도 아무 오류가 나지 않는다** — 그게 이 프로젝트에서 가장 비싸게 배운
것이다. 자세한 사례는 [V3_HANDOFF.md 8.-5](V3_HANDOFF.md)에 있다.

## 기술

| 영역 | 스택 |
|---|---|
| 백엔드 | FastAPI, psycopg2, Supabase(Postgres) — 라우터 18개, 엔드포인트 51경로 |
| 프론트 | Vite, React 19, TypeScript 6, React Router 7 — 화면 12개 |
| 테스트 | pytest 322개, Vitest 189개 |
| 배포 | Render (정적 사이트 + 웹 서비스), 무료 티어 |
| 접근성 | Lighthouse 100점 (모바일) |

### API 응답 타입은 손으로 쓰지 않는다

`scripts/dump_openapi.py`가 저장소 코드에서 OpenAPI 명세를 뽑고 `openapi-typescript`가
프론트 타입을 만든다. CI가 그 둘의 어긋남을 검사하므로, 백엔드 응답 모양이 바뀌면
프론트 빌드가 먼저 깨진다.

명세를 **배포된 서버가 아니라 저장소 코드에서** 뽑는 것이 요점이다. 처음에는 배포된
쪽에서 받았는데, 그 명세에 이미 지운 엔드포인트가 남아 있었다.

### 왜 SSR을 안 썼나

레시피 상세가 검색엔진에 잡히려면 SSR이 유리하다. 그런데 **백엔드 콜드스타트 동안
SSR은 오히려 해롭다.** 서버가 렌더링하려면 API를 기다려야 하는데 그 API가 15분 유휴
후 잠들기 때문이다. 정적 SPA는 셸이 즉시 뜨고(0.29초) 그 위에 "서버 깨우는 중"을
띄울 수 있다.

## 구조

```
api/          FastAPI 라우터 (18개) — 얇은 HTTP 래퍼
src/agents/   도메인 로직 — 추천·인증·영양·안전 등
frontend/     React 앱
migration/    Postgres 스키마 (001~008, 순서대로 적용)
scripts/      운영 도구 (배포 점검·백업·초기화 링크·계정 삭제)
tests/        pytest
docs/         작업 기록
```

라우터는 얇게 유지한다. 도메인 로직은 `src/agents/`에 있고 라우터는 HTTP 관심사(인가,
상태 코드, 요청 검증)만 다룬다.

## 개발

```bash
python -m venv .venv && ./.venv/Scripts/python.exe -m pip install -r requirements-dev.txt
```

```bash
./.venv/Scripts/python.exe -m pytest -q
```

```bash
cd frontend && npm ci && npm run dev
```

`.env`에 `POSTGRES_URL`이 필요하다. 필요한 환경변수 전체는 `render.yaml`에 선언돼 있고,
`tests/test_deploy_config.py`가 코드가 읽는 이름과 그 선언을 대조한다 — 새 환경변수를
읽는 코드를 쓰면 이 테스트가 먼저 깨진다.

> **로컬에서 성능을 잴 때는 `127.0.0.1`을 쓸 것.** Windows에서 `localhost`는 IPv6로
> 먼저 풀리는데 uvicorn은 IPv4에만 바인딩돼, 매 요청에 2초가 얹힌다(실측 2038ms vs 4ms).

### 배포 점검

```bash
./.venv/Scripts/python.exe scripts/smoke_test_deploy.py
```

배포된 서비스를 35항목으로 실제로 태운다 — 가입부터 추천·즐겨찾기·후기·레시피 등록까지
지인이 밟을 흐름 그대로다. CORS는 "Render 정적 사이트 → Render API"라는 경계에서만
검증되므로 로컬 테스트가 덮지 못한다.

**흔적을 남기지 않는다.** 검증 계정을 스스로 만들고 지우고, 공개 레시피에 누른 추천은
확인 후 다시 눌러 되돌리며, 등록한 레시피는 삭제 경로로 지운다(그 삭제 자체가 검사
항목이다). 중간에 실패해 남은 것이 있으면 계정 정리 단계가 함께 걷어낸다.

## 알려진 제약

**비밀번호 초기화 메일이 나가지 않는다.** Render 무료 웹 서비스가 SMTP 포트를 막는다.
자격증명 문제가 아니라 플랫폼 제약이다 — 같은 코드가 로컬에서는 2.5초에 발송된다.
화면은 이 사실을 그대로 말하고, `scripts/make_reset_link.py`로 링크를 직접 만들어
전달한다.

**추천이 웜 상태에서 2.4초 걸린다.** 무료 티어가 0.1 CPU라 CPU 바운드 구간만 증폭된다.
같은 서버에서 DB 바운드인 검색은 0.61초다. 로컬에서는 이미 0.674초 → 0.20초까지 줄인
뒤의 숫자라, 더 짜내려면 알고리즘을 손대야 한다.

**엔드포인트 51개 중 화면이 부르는 것은 34개다.** 남은 17개는 가격·쇼핑·안전정보·
제철·인기영상·재료 즐겨찾기·후기 AI 요약이다. 후기 요약은 호출마다 비용이 붙는데
지금 후기가 1개뿐이라 미뤘고, 나머지는 무엇이 쓸모 있는지 아직 아무도 모르기 때문이다.
지인 테스트에서 요청이 나온 것부터 잇고, 안 나온 것은 지운다.

## 이력

V1(CLI) → V2(Reflex 단일 페이지) → V3(React).

V2는 28일간 기능 84개를 완성하고 배포까지 마쳤지만 **실사용자가 0명이었다.** 가입 43명
중 냉장고에 재료를 넣은 사람이 3명이었다. V3는 기능을 더 만드는 대신 화면을 9개로
줄이고, 대신 **어디서 이탈하는지 볼 수 있게** 사용 로그를 심었다.

구조적으로 가장 큰 변화는 라우팅이다. V2는 화면 전체가 단일 페이지라 레시피 상세를
링크로 공유할 수 없었고 뒤로가기도 동작하지 않았다. V3에서 진짜 URL로 쪼갠 것이 이번
전환의 가장 실질적인 이득이다.
